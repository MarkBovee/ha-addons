# Prompt: battery-manager decision trace + margin fixes

Context: battery-manager (0.8.x, repo ha-addons, `battery-manager/app/main.py`) is being replaced by HEMS v2, but must stay usable until then. Observed on 2026-10-07/08 (HA data + code read, not yet confirmed with logs because the add-on log only keeps ~1 hour):

1. 2026-10-07 evening: only 1 h sold (17:45-18:00 and 18:30-19:15, 8000 W, @ ~0.465-0.47 export), battery left at 52% SoC, plan then `Adaptive 0W` for 19:15-22:00 while the price was still 0.42 -> 0.38. Gap 18:00-18:30 between two sell windows although prices there were as high.
2. Same night: grid charge 21:45-22:00 @6500 W and 22:45-00:00 @7000 W (price 0.334/0.315), 46% -> 80% SoC, to sell tomorrow 08:00 (0.401) and 19:00 (0.422). Margin ~0.09-0.11 before ~10% round-trip loss, i.e. below `min_profit_threshold` (0.10) once losses count.
3. Planned charge power for the midday window 11:30-16:30 jumps 8000 W (19:15) -> 946 W (00:00) -> 500 W (02:00) -> 1600 W (06:00) -> 1046 W (07:00) as SoC/solar inputs change. Charge blocks for the night rise 1061 W -> 7000 W between 16:15 and 22:45.
4. `Schedule published` is logged every minute while adaptive discharging (full schedule re-published on each adaptive power change).
5. Price ranges / top-X are computed per calendar day (`_split_curve_by_date`, `calculate_price_ranges`); evening decisions only see the rest of today. Min-profit margin is `min(import of the day) + min_profit` (calculate_price_ranges), not the cost basis of the energy in the battery.

Tasks (keep changes small, no redesign; HEMS replaces this later):

A. Decision trace (most important). On every schedule generation (every 15 min and on regeneration) append ONE JSON line to `/data/decision_trace.jsonl` (rotate at ~20 MB or 14 days): timestamp (UTC + local), SoC, temperature + effective discharge hours, import/export price now, day min import, load/discharge/adaptive ranges, the list of discharge windows before and after `_filter_supported_discharge_windows` (with the reason a window was dropped or truncated: rank, needed kWh, available kWh, reserve floor), sell-buffer result, solar-aware numbers (deficit, remaining solar, usable, grid target), precharge decision, final published charge/discharge periods and charge power per period. Expose the last record as attributes on a new sensor (`sensor.battery_manager_decision`) and log the same one-liner at INFO. Also log the reason when the plan for an unchanged quarter changes power by >25%.
B. Margin check for grid charging that is not in a top-X charge slot (solar-aware grid target, sell-buffer precharge, overnight): only charge when `expected_sell_price * 0.90 - charge_price >= min_profit_threshold`, where expected_sell_price is the price of the window the energy is meant for. Otherwise skip and log the reason. Add an option `grid_charge_min_margin` (default = `min_profit_threshold`) and `round_trip_efficiency` (default 0.90).
C. Margin basis in `calculate_price_ranges`/`find_profitable_discharge_starts`: today it is the day's cheapest import price + `min_profit_threshold`. Add option `margin_basis: day_min_import | solar_export` (default day_min_import, no behaviour change) where `solar_export` uses the lowest export price in the planned or actual PV charge window as cost basis (energy from PV costs the forgone export price). Verify with unit tests built from the 2026-10-07 curves (import ~0.31 midday, evening 0.40-0.47).
D. Explain and, if it is a bug, fix the gap in sell windows (18:00-18:30 between 17:45-18:00 and 18:30-19:15 on 2026-10-07): reproduce in a test with the price curve and SoC trajectory (SoC 36% at 12:00, 87% at 18:00) and check whether windows are chosen by price order or cut by `_filter_supported_discharge_windows` using the current SoC instead of the projected SoC at window start. Projected SoC (current + scheduled charge - earlier discharge) at each window start is the correct input.
E. Stability: do not recompute `charge[0]` power for an active or upcoming window more than once per hour unless SoC deviates >5 pp from the projection or the solar forecast changes >25%; log when it does.
F. Publish the schedule to battery-api only when the content of the published periods changes (adaptive power steps below 100 W do not count).
G. Sell hours counted after charging (agreed with Mark). Currently `top_x_discharge_hours` (and the temperature cap) select the highest-priced quarters of the whole calendar day. Change this to: pick the X best discharge quarters from the quarters AFTER the end of the charge window (end of the last top-X charge slot / main charge window of that day) until the next charge window (or end of known prices, including tomorrow's curve once published). Quarters before the charge window (e.g. a 08:00 morning peak) do NOT consume the X-hour budget and must NOT trigger grid pre-charging; before the charge window only sell what is already in the battery above the reserve floor (adaptive/sell-wait logic stays). Add option `discharge_after_charge_only: true` (default true). Tests with the 2026-10-07/08 curves: charge window 11:15-16:00, X=2 -> sell hours must be inside 16:00-24:00 and the 08:00 window must not produce the night charge 21:45/22:45.

Acceptance: unit tests for B, C, D with the 2026-10-07 data; decision trace file written and readable; no change in behaviour for days with clear spread (e.g. 2026-10-06: sold 7.1 kW 18:00-20:00 @0.54-0.59). Do not touch battery-api.
